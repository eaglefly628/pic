# 产品化架构：App Store 三端 + 本地账户 + 可选云备份

> 定位（2026-08）：作为付费/免费 App 上架 App Store（iPhone / iPad / Mac）。
> 用户下载后在**本机**建立自己的账号，**数据存在自己设备上**；
> 云端只提供**可选**的备份服务，且是**纯文件服务**——服务端只见密文，永远没有解密密钥。

---

## 一、为什么这个方向是对的

它把「产品化」最难的一块直接绕开了：

| | 服务端账户型（如常见 SaaS） | **本架构：本地优先** |
|---|---|---|
| 用户数据存哪 | 服务端数据库，需多租户隔离 | **用户自己设备**，天然隔离 |
| 服务端泄露后果 | 全量用户数据 | 只有一堆**打不开的密文** |
| 上架前必须有服务端 | 是 | **否**（阶段一纯本地即可上架） |
| 合规负担 | 高（数据保管者） | 低（不保管可读数据） |
| 断网可用 | 否 | 是 |

**结论：阶段一完全不需要写任何服务端**，先把纯本地版上架；云备份作为后续版本更新加上。这是最快的上架路径，也是风险最低的。

## 二、整体架构

```
┌─ 设备（iPhone / iPad / Mac）─────────────────────────┐
│                                                       │
│  原生壳（推荐 Tauri 2：一套代码出 macOS + iOS）       │
│   │                                                   │
│   ├─ WebView：现有 hub + 四个子应用（前端逻辑基本不动）│
│   │                                                   │
│   └─ 原生层                                           │
│       ├─ 文件存储  ← 取代 localStorage / IndexedDB    │
│       ├─ Keychain  ← 存「被生物识别包裹的数据密钥」   │
│       ├─ Face ID / Touch ID（LocalAuthentication）    │
│       └─ 云备份客户端（上传的已经是密文）             │
└───────────────────────────────────────────────────────┘
                        │  只上传/下载不透明密文 blob
                        ▼
┌─ 云备份服务（可选，阶段二）─────────────────────────┐
│  账户：邮箱 + 密码 —— 只用于「你是谁 / 配额多少」     │
│  存储：密文 blob + 版本历史（照搬现有 40 份轮转设计） │
│  ❗ 服务端没有、也不可能有解密密钥                    │
└───────────────────────────────────────────────────────┘
```

## 三、本地账户与密钥设计

### 用户名的定位
用户名**不参与加密**，它只是标识——用于（a）同一台设备上多账号切换，（b）将来绑定云备份账户。
**真正的安全边界是主密码。**

### 密钥结构（沿用并统一现有 project-one 的信封加密）

```
主密码 ──PBKDF2/Argon2──► KEK-A ──┐
                                   ├──► 包裹同一把 DEK ──► DEK 解密全部数据
恢复密钥 ─────────────────► KEK-B ──┘
                                   
生物识别：DEK 再被 Keychain 中的密钥包裹一份，Face ID 通过即可取出
```

一把数据密钥（DEK），被多把钥匙分别包裹。好处：改主密码只需重新包裹 DEK，**不必重新加密全部数据**（现有理财模块已经是这个结构，可直接复用）。

### ❗ 恢复密钥：产品化的必答题

零知识加密的必然代价是：**忘记主密码 = 数据永久打不开**。自己用可以接受，**做成产品不行**——用户一定会忘，然后来找你要数据，而你按设计就是拿不出来。

行业标准解法（1Password Secret Key、Bitwarden Recovery Code 都是这个思路）：

- 建账号时生成一串**恢复密钥**（如 26 位 Base32），要求用户抄下来或存进系统密码管理器
- 它单独包裹一份 DEK，忘密码时用它重设主密码
- 引导流程里必须强制用户确认已保存（让他回填一次）

**这一条不做，上线后会是最大的客服灾难和差评来源。**

## 四、存储层迁移（阶段一最关键的工程）

### 问题
现在所有数据都在 `localStorage` + `IndexedDB` 里。装进 WKWebView 之后：
**iOS 在存储压力下会清理 WebView 的这两种存储**，`navigator.storage.persist()` 在 iOS 上并不能豁免。
对一个「用户把全家财务和密码放进去」的付费 App，这是不可接受的丢数据风险。

### 解法
数据落到**原生文件**（App 容器目录），由原生层负责读写。

### 好消息：迁移接口已经现成
hub 里的 `buildBundle()` / `applyBundle()` 已经是「把全部数据序列化成一个包 / 从一个包还原」的完整抽象——这正是天然的迁移边界。

只需定义一层 `StorageProvider`：

| 实现 | 用途 | 落地方式 |
|---|---|---|
| `WebStorageProvider` | 浏览器/开发调试 | 现有 localStorage + IndexedDB |
| `NativeStorageProvider` | 上架的 App | 原生文件（+ Keychain 存密钥） |

前端业务代码不用改，只换 Provider。

## 五、云备份服务（阶段二，可延后）

**它必须简单到「就是个文件服务」**：

- 接口只有三个：上传密文、下载最新密文、列出历史版本
- 上传前客户端已加密；服务端拿到的是不透明字节
- ❗ **加密密钥绝不能是云账户密码**——必须由主密码派生的独立密钥。否则「服务端知道账户密码 = 能解密数据」，零知识就破了
- 冲突处理可直接复用现在本地已实现的那套（`baseSavedAt` 过期写检测 + 冲突自动留底）

## 六、App Store 特有约束（容易漏、但会卡审核）

| # | 约束 | 说明 |
|---|---|---|
| 1 | **云备份若收费 → 必须走 App 内购买（IAP）** | 指南 3.1.1：App 内消费的数字服务不能用外部支付，苹果抽成 15–30%。**这是商业模型问题，要提前算进定价** |
| 2 | **有账户创建 → 必须提供 App 内删除账户** | 指南 5.1.1(v)，强制。云备份账户尤其适用 |
| 3 | **加密出口合规声明** | `ITSAppUsesNonExemptEncryption`。用标准加密（AES/TLS）通常可走豁免，但必须如实填写 |
| 4 | **磁盘清理功能必须砍掉** | 删 `~/Library/Caches`、清废纸篓在沙盒内做不到；且「永远连不上、只显示报错」的整页占位容易被判 4.2 最低功能 |
| 5 | **看球模块的盘口（odds）建议隐藏** | 可能触发博彩相关审核关注与年龄分级 |
| 6 | **隐私营养标签如实申报** | 本机存储、照片 GPS 反查（发给 OpenStreetMap）、行情/比分 API、云备份 |
| 7 | **宣传与实现必须一致** | 指南 2.3.1。当前「本地加密」的说法在开发世界模块（硬编码密码）尚不成立，上架前必须修 |

## 七、分阶段路线

### 阶段一：纯本地版上架（**不需要任何服务端**）
1. 定壳技术栈（推荐 Tauri 2）并搭起工程
2. **存储层迁移**到原生文件（`StorageProvider` 抽象）
3. **本地账户 + 恢复密钥**流程
4. 修掉硬编码密码（`AUTO_PW`）、统一 KDF 到 600k（含老数据迁移）
5. 砍磁盘清理、处理盘口显示
6. 三端响应式改造（详见 `APPLE_REVIEW.md` 第三、四节）
7. 生物识别接原生 LocalAuthentication（替代 WebAuthn）
8. 签名 / 公证 / entitlements / 隐私清单 / 商店素材

→ **此时即可提交审核**

### 阶段二：云备份（后续版本更新）
9. 文件服务 + 账户体系 + 配额
10. IAP 接入（若收费）+ 账户删除入口
11. 端到端加密备份流程与冲突处理（复用现有协议）
